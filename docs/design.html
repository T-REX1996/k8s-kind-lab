k8s-kind-lab / design v8

kubeadm で K8s を一通り学ぶ。設計方針

Google Cloud の VM 3 台に kubeadm で K8s のクラスタを作り、API サーバとワーカ、CPU の vLLM を載せて学ぶ。その先で Istio、Argo CD、Agent Substrate、kagent 1.0、agentgateway を動かし、kagent の OSS 活動と、Zenn の記事につなげる。

2026-11-22 更新学習用リポジトリ方針の段階。コードは未着手

v8 での変更。サブネットを 2 つに分けました。control-plane 用が 10.10.0.0/27、worker 用が 10.10.0.32/27 です。3 台とも同じゾーンに置き、Cloud NAT は両方のサブネットを対象にします。
v7 での変更。クラスタを Kind から kubeadm に変え、本物の VM 3 台(control-plane 1 台と worker 2 台)にしました。外へ出る方法は Cloud NAT で、VM に外部 IP は付けません。学んだことは、Zenn の記事にします。
v2〜v6 の変更。kagent 1.0 の前提、Terraform、Istio、ネットワーク構成を追加しました。

このページは設計の考え方だけを書いています。マニフェストとアプリのコードは自分で書き、詰まったらヒントとレビューをもらう進め方です。数値の見積りは目安で、実測してから直します。リポジトリ名は k8s-kind-lab のままで、kubeadm に合わせて変えるかは、まだ決めていません。

目的と制約

目的

  • kubeadm でクラスタを作り、control-plane と worker の仕組みを理解する
  • Pod、Service、Ingress、Job、HPA、NetworkPolicy、RBAC を手で触って理解する
  • Terraform で、ネットワークと VM をコードにして、作り直せるようにする
  • Ingress で入口の基本を理解したあと、Istio に移行して、違いを説明できるようにする
  • Git を正とするデプロイ(Argo CD)に移行し、違いを体感する
  • kagent 1.0 が K8s の上でどう動くのかを理解する
  • agentgateway で、エージェントの通信を一か所に通す
  • kagent の OSS に小さな貢献をする足場を作り、学んだことを Zenn の記事にする

制約

  • 手元の Mac は Intel i5、メモリ 16GB。複数ノードのクラスタは動かせない
  • GKE の常時課金は避ける。GPU は使わない
  • 外部の LLM API は使わない。推論はクラスタ内の vLLM(CPU)
  • kagent 1.0 の前提で、Kubernetes は 1.37 以上。パッケージの提供状況は、着手時に確認する
  • 予算アラートは、今は見送り。止め忘れを自動停止で防ぐ

全体構成

専用の VPC の中に、サブネットが 2 つ(control-plane 用と worker 用)、VM が 3 台あります。VM は内部 IP だけを持ち、外へは Cloud NAT で出ます。入口は、IAP 経由の SSH だけです。

青い枠は、段階 2〜3 で自分が手を動かす部分です。破線は、後の段階で足す部分です。Cloud NAT は、2 つのサブネットの両方が対象です。Pod のネットワークの範囲は、CNI を選んでから決めます。

ネットワーク構成

要素内容
VPC専用のものを 1 つ。サブネットは自動で作らない。既定のネットワークは使わない(既定のネットワークには、SSH を全世界に開くルールが付いている場合がある)
サブネット2 つ。control-plane 用 10.10.0.0/27、worker 用 10.10.0.32/27(それぞれ 32 個のアドレス。予約を除いて、使えるのは約 28 個)。VM は 3 台なので足りる。Pod と Service の範囲は、別にある
ファイアウォール(IAP)TCP 22 を、IAP の範囲(35.235.240.0/20)からだけ許可する。対象は、タグで絞る
ファイアウォール(ノード間)ノード同士の通信を許可する。API サーバ、etcd、kubelet、NodePort、CNI のポートなど。必要なポートは、kubeadm と CNI の公式ドキュメントで確認する。VM にネットワークタグ(control-plane、worker)を付け、役割ごとに許可する相手を絞る。サブネットの範囲でも絞れる
外へ出る方法Cloud Router と Cloud NAT。VM に外部 IP は付けない。2 つのサブネットの両方を、NAT の対象に入れる。NAT の外部 IP は、自動で割り当てる設定にする案(要確認)
SSHIAP 経由と OS Login。VS Code の Remote SSH も、同じ経路を使う
公開するポートなし。80、443、6443、NodePort は、外に開けない。画面は IAP のポート転送で見る
VM の内部 IPVM を止めても、内部 IP は残る見込み。ノードの IP が変わらないよう、予約するかを検討する(要確認)
ゾーン3 台とも、同じゾーンに置く。同じゾーンの内部 IP の通信は無料で、ゾーンが違うと、通信量の課金がある。サブネットを分けても、この単価は変わらない(公式の料金ページで確認する)

使わない部品

部品本来の役割今回
ロードバランサ外から複数の VM に振り分ける使わない。外に公開しない
固定の外部 IP再起動しても変わらない IP使わない。SSH は IAP 経由で、IP に依存しない
VPN自宅や会社のネットワークと、VPC をつなぐ使わない。IAP で足りる

IP の範囲

ノードのサブネットと、Pod、Service の範囲が重ならないようにします。Pod の範囲は、選ぶ CNI の既定の値によって変わります。

用途範囲備考
サブネット(control-plane 用)10.10.0.0/27自分で決めた範囲。約 28 個のアドレスが使える
サブネット(worker 用)10.10.0.32/27自分で決めた範囲。約 28 個のアドレスが使える
Pod未定kubeadm init の --pod-network-cidr と、CNI の設定で決める。CNI ごとの既定の値は、サブネットと重ならないか確認する
Service未定kubeadm の既定の値を使う案。公式ドキュメントで確認する

Mac から画面を見る流れ

  1. 接続Mac から、IAP 経由で control-plane か worker に SSH でつなぐ。Mac → IAP → VM
  2. ポート転送Mac の localhost のポートを、VM の NodePort につなぐ(-L または IAP のトンネル)。Mac:8080 → VM:NodePort
  3. 表示Mac のブラウザで、Ingress の画面を見る。外には公開しない。ブラウザ → localhost

LoadBalancer の扱いは、確認が必要です。kubeadm のクラスタには、外のロードバランサがないので、Service の種類を LoadBalancer にすると Pending のままになります。MetalLB の L2 方式は、Google Cloud の VPC では使えない可能性があります(要確認)。まずは NodePort とポート転送で進めます。

通信の流れ

アプリ(段階 3)

CPU の vLLM は遅いので、API は推論の完了を待ちません。受け付けてから後で結果を取りに来てもらう、非同期の形にします。

  1. 投入クライアントが API にプロンプトを送る。Ingress → api
  2. 受付API はジョブ ID を発行して Redis に積み、すぐ ID を返す。api → data
  3. 取り出しワーカがキューからジョブを取り出す。worker ← data
  4. 推論ワーカが vLLM の Service に問い合わせる。worker → llm
  5. 保存ワーカが結果を Redis に書く。worker → data
  6. 取得クライアントがジョブ ID で結果を取りに来る。Ingress → api → data

エージェント(段階 6〜7)

kagent のセッションは、Substrate 上のアクターとして動きます。段階 7 で agentgateway を入れると、LLM への問い合わせがそこを通ります。

  1. 会話ユーザーが kagent のエージェントに話しかける。クライアント → kagent
  2. セッションセッションが作られ、サンドボックス内のアクターが動く。履歴は PostgreSQL に残る。kagent → substrate
  3. LLM 呼び出しエージェントが LLM に問い合わせる。ModelConfig の向き先が agentgateway になる。substrate → agentgateway
  4. 中継agentgateway が vLLM に中継し、通信をログに残す。agentgateway → llm
  5. ツールツールは kagent の外にある MCP サーバを呼ぶ。RemoteMCPServer で登録する。agentgateway → MCP サーバ

設計判断と理由

決めたこと理由検討した代替
クラスタは kubeadm で、本物の VM に作るcontrol-plane と worker の仕組みを、組み立てるところから理解したい。ノード間のネットワークや、ノードの障害も体験できる。gVisor が動く可能性も高い。CKA の範囲にも関わる。Kind(軽くて速いが、クラスタ構築は学べない)。併用(費用と手間が増える)。
control-plane 1 台と worker 2 台最小の複数ノード。配置、障害、ノードの追加が学べる。台数分の費用を、抑えられる。worker 3 台(費用が増える)。単一ノード(学べる範囲が狭い)。
サブネットは 2 つに分ける(control-plane 用 10.10.0.0/27、worker 用 10.10.0.32/27)役割ごとにネットワークを分ける、実務に近い形を練習できる。ファイアウォールを、サブネットの範囲でも絞れる。VM 3 台には、それぞれ十分な大きさ。費用は、ほぼ変わらない見込み。1 つの /26(設定は少ないが、分離の練習ができない)。/24(必要以上に広い)。
外へは Cloud NAT で出る。VM に外部 IP は付けないノードがインターネットから見えない。3 台なら、外部 IP を台数分付けるより、費用も同程度かやや安い見込み。Terraform で Router と NAT を学べる。外部 IP を台数分(簡単だが、ノードが公開される)。
専用の VPC と、IAP 経由の SSH だけにする外に何も公開せず、入口を 1 つに絞れる。IP が変わっても、SSH の設定を直さなくてよい。既定のネットワークと、自分の IP だけを許可する方式。
VM とネットワークは Terraform で作る最初から作り直せる。台数が増えても、同じコードで済む。課金が発生しない題材から始められる。コンソールで作る(再現できない)。
マシンタイプは小さく始める段階 1 は軽い。メモリが必要な段階の前に、停止中に変えれば、無駄な課金を避けられる。最初から大きいマシン(使わない間も高い)。
kagent は 1.0 を使うOSS への貢献は、現行の main(1.x)が対象。0.10.x は 1.0 に置き換えられた。0.10.x で先に慣れる(後でやり直しになる)。
Substrate と PostgreSQL を、kagent の前に入れる1.0 の前提で、エージェントはこの上で動く。先に単体で確認すると、原因を切り分けやすい。kagent と同時に導入(失敗したとき、どこが悪いか分からない)。
Ingress を学んでから Istio に移る段階 1 は素の K8s の動きを見たい。同じ入口を後で置き換えると、違いがはっきり分かる。最初から Istio(重く、基礎が見えにくい)。
LLM の通信は agentgateway を通すGateway API に準拠していて、vLLM の登録手順が公式にある。通信のログと上限を、一か所で見られる。kagent から vLLM に直接(段階 6 で先に試す)。kgateway は使わない。
先に手書き、後で GitOps先に kubectl apply で仕組みを理解してから Argo CD に任せると、自動化されていることが分かる。最初から Argo CD。
学んだことを Zenn の記事にする理解を、人に説明できる形にして、定着させる。kagent の連載の続きにもなる。ノートのまま残す。
バージョンは着手時に確認して固定どの製品も更新が速い。推測せず、公式のリリース情報から決めて CLAUDE.md に記録する。latest(再現できなくなる)。

リスクと、最初に確かめること

新しいものが多く、資料も少ないので、動かないことを前提に、確認の順番を決めておきます。

リスク確かめ方だめだったとき
Kubernetes 1.37 以上のパッケージが無い段階 0b の前に、kubeadm の公式ドキュメントとパッケージの提供状況を確認する。提供される最新の版で始め、kagent 1.0 の前提との差を記録する。
kubeadm の手順で、つまずく公式ドキュメントの順に進め、各ステップで状態を確認する。つまずきは、手順書に記録する。VM を作り直して、やり直す(Terraform)。
CNI の選択で迷うNetworkPolicy に対応しているか、Pod の範囲が重ならないかを確認する。先に一つ選んで進め、段階 4 の前に、入れ替えを検討する。
Cloud NAT の設定を間違えて、外に出られないVM 作成後すぐに、外へ出られるか(パッケージの取得)を試す。一時的に、外部 IP を付けて切り分ける。
サブネットを分けたため、ファイアウォールのルールを間違えて、ノード間で通信できないVM を作ったあとに、control-plane と worker の間で、ping や、API サーバのポートへの接続を試す。一時的に、ノード間の通信をすべて許可して切り分け、必要なポートだけに絞り直す。
IAP 経由の SSH が通らないVM を作った直後に、IAP の API、ファイアウォールの範囲、権限を確認する。自分のグローバル IP だけを許可する方式に、一時的に切り替える。
LoadBalancer が Pending のままになる段階 1 の G の前に、NodePort の使い方を調べる。MetalLB は、Google Cloud の VPC で使えるかを調べる。NodePort とポート転送で見る。
VM を止めて起動し直すと、ノードが戻らない段階 1 の H で、わざと止めて起動し直し、挙動を観察する。内部 IP が変わらないか確認する。kubeadm のノードの状態を確認し、必要ならクラスタを作り直す。
gVisor が動かない段階 6a の最初に、WorkerPool でサンドボックスを 1 つ動かす。別の分離クラス(microvm)を調べる。VM 側の設定が必要になる可能性がある。解決しなければ、原因を記録して 0.10.x に切り替える。
Istio と agentgateway で、入口の役割が重なるどちらも Gateway API を扱える。段階 4b の前に、GatewayClass で担当を分ける方法を調べる。段階 7 の前に、Istio の入口を片付ける。または、Istio は一部の namespace だけに限る。
Istio のモードの選択で迷うsidecar 方式と ambient 方式がある。着手時に、公式ドキュメントで現在の推奨と、kagent 1.0 との相性を調べる。通信の仕組みを学ぶ目的に合う方を選ぶ。合わなければ、対象の namespace を絞る。
資料が少なく、情報が古い公式ドキュメントとリリースノートを最優先にする。0.x 向けの記事は参考程度にする。Issue を調べ、見つからなければ自分で書く。貢献の種になる。
成熟度が alpha かもしれない着手時に、リリースノートと GitHub のリリースページを確認する。壊れる前提で、作り直せる手順を残す。
止め忘れで、課金が続く自動停止のスケジュールを、最初のコードに入れる。作業の終わりに、VM とディスクの状態を確認する。予算アラートは見送り中。長く使わないときは、Terraform で VM を消す。
Terraform の状態ファイルをコミットしてしまう.gitignore に、*.tfstate、.terraform/、*.tfvars を入れてある。コミット前に git status で確認する。気づいたら、履歴から消す方法を調べる。
ブログに、実値を載せてしまうプロジェクト ID、請求アカウント ID、メールアドレス、IP は、伏せるか、ダミーにする。スクリーンショットも確認する。公開前に、記事全体を読み直す。

費用を抑える運用

  • 使うときだけ起動する。全 VMを停止すると、CPU とメモリの課金は止まるが、ディスクは台数分、課金が続く
  • 夜間の自動停止(インスタンススケジュール)を、VM と同じ Terraform のコードに入れて、止め忘れを防ぐ
  • Cloud NAT は、VM 台数分の時間課金と、通信量(1 GiB あたり)の課金がある。外部 IP を台数分付ける方式と比べて、同程度かやや安い見込み。単価は公式の料金ページで確認する
  • 固定の外部 IP は使わない。ロードバランサも使わない
  • サブネットを 2 つに分けても、費用は、ほぼ増えない見込み。VM は 3 台とも同じゾーンに置き、ノード間の通信を無料にする。Cloud NAT は、両方のサブネットで 1 つを共用する
  • 最初は小さな VM で始め、メモリが必要になる段階で、停止中にマシンタイプを変更する。変更できる条件は、公式ドキュメントで確認する
  • 長く使わないときは、Terraform で VM とディスクを消す。作り直せるよう、手順と設定をリポジトリに残す
  • 最初は通常の VM。慣れたらスポット VM を試す(突然止まることがある)
  • 予算アラートは見送り中。気が向いたら、Terraform で作る。通知先は、請求アカウントの管理者へのメールが既定

VM の作成と課金に関わる設定は、内容を確認してから実行します。金額は、実際のマシンタイプとリージョンが決まってから、料金計算ツールで見積もります。
