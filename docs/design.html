k8s-kind-lab / design v5

Kind で K8s を一通り学ぶ。設計方針

API サーバとワーカ、CPU の vLLM を Kind に載せて K8s を学ぶ。その先で Argo CD、Agent Substrate、kagent 1.0、agentgateway を動かし、kagent の OSS 活動につなげる。

2026-11-21 更新学習用リポジトリ方針の段階。コードは未着手

v5 での変更。Terraform を、段階 0b として追加しました。予算アラートを VM の前に Terraform で作り、手で作った VM を Terraform で再現します。GCP のプロジェクトは作成済み(組織の下)で、gcloud と Terraform も Mac に入れてあります。
v4 での変更。Ingress で入口の基本を学んだあと、Istio に移行する段階 4b を追加しました。
v3 での変更。最初から Google Cloud の VM で Kind を動かす前提にし、段階 0(VM を整える)と段階 1(control-plane、worker、Service、Ingress の観察)の進め方を追加しました。
v2 での変更。kagent は 1.0 を使います。1.0 は Agent Substrate、PostgreSQL、Kubernetes 1.37 以上を前提にするため、段階 6 を二つに分け、worker を 3 台に増やす案を入れました。

このページは設計の考え方だけを書いています。マニフェストとアプリのコードは自分で書き、詰まったらヒントとレビューをもらう進め方です。数値の見積りは目安で、実測してから直します。

目的と制約

目的

  • Pod、Service、Ingress、Job、HPA、NetworkPolicy、RBAC を手で触って理解する
  • Terraform で、予算アラートと VM をコードにして、作り直せるようにする
  • Ingress で入口の基本を理解したあと、Istio に移行して、違いを説明できるようにする
  • Git を正とするデプロイ(Argo CD)に移行し、違いを体感する
  • kagent 1.0 が、K8s の上でどう動くのかを理解する
  • agentgateway で、エージェントの通信を一か所に通す
  • kagent の OSS に、小さな貢献をする足場を作る

制約

  • 手元の Mac は Intel i5、メモリ 16GB。全部同時に動かすには足りない
  • GKE の常時課金は避ける。GPU は使わない
  • 外部の LLM API は使わない。推論はクラスタ内の vLLM(CPU)
  • kagent 1.0 の前提で、Kubernetes は 1.37 以上。Kind のノードイメージは着手時に確認する

最初の一歩。段階 0 と 1

最初から Google Cloud の VM で Kind を動かします。まず VM を整え(段階 0)、次に control-plane と worker の仕組み、Service、Ingress を観察して理解します(段階 1)。環境を一つにそろえておくと、後の段階で移行する手間がありません。

段階 1 で観察すること

用語の整理。Service は Pod の前に置く、仮想 IP(ClusterIP)を持つ入口で、実体は各ノードの kube-proxy が作る転送ルールです。Ingress は HTTP の振り分けルール(ホスト名やパス)を書くリソースで、動かすのは Ingress controller です。Istio の Gateway と VirtualService は、段階 4b で、Ingress と比べながら扱います。Ingress の次世代にあたる Gateway API は、段階 7 の agentgateway につながります。

順テーマ観察すること調べる用語
AKind の正体docker ps で見えるノードと、kubectl get nodes -o wide の対応kubeadm、containerd、kindest/node
Bコントロールプレーンkube-system の Pod が何で、どこで動くか。control-plane の設定ファイルが置かれる場所kube-apiserver、etcd、scheduler、controller-manager、static Pod
CPod 作成の流れPod を 1 つ作り、describe の Events で、スケジュール、取得、起動の順を追うkubelet、watch、reconcile
Dワーカノードのコンテナに入り、kubelet と containerd を見る。worker のコンテナを止めたとき、Pod が何秒後にどうなるかノードの Ready、taint、eviction
EServiceClusterIP を作り、ノード内の転送ルールで実体を探す。CoreDNS で名前が引けることkube-proxy、iptables、EndpointSlice、CoreDNS
FIngress2 つのアプリを、パスで振り分けるIngress controller、IngressClass、extraPortMappings

B〜D は、予想を書いてから実行し、結果と見比べる進め方にします。「止めたらどうなるか」を先に予想すると、仕組みが頭に残ります。

Kind の設定で調べる点

  • ノードの role を並べて、control-plane 1 台と worker 3 台を指定する方法
  • ホストのポートをノードに通す extraPortMappings
  • Ingress controller を載せるノードに付けるラベル(Kind の公式ドキュメントの Ingress の節)

成果物

  • docs/01-k8s-basics.md に、control-plane と worker の図と各部品の役割を書く
  • Pod 作成の流れと、Service と Ingress の違いを、自分の言葉で書く
  • 「予想と結果が違った点」を残す

Ingress controller の選択は、着手時に決めます。以前よく使われた ingress-nginx は、メンテナンスが終わる発表があったはずですが、確認できていません。Kind の公式ドキュメントと各プロジェクトの現状を見て選びます。

公式の 1.0.0 リリースノートと、0.x からの移行手順で確認した内容です。0.x と同じ感覚では動かないので、設計に影響する点だけを挙げます。

項目1.0 での扱い設計への影響

全体構成

Google Cloud の VM を 1 台用意し、その中で Kind を動かします。ノードは control-plane 1 台と worker 3 台の案です。worker-3 はエージェントの実行専用にします。

青い枠は段階 2〜3 で自分が手を動かす部分です。破線は後の段階で足す部分です。worker-3 の専用化は案で、まだ決めていません。

通信の流れ

アプリ(段階 3)

CPU の vLLM は遅いので、API は推論の完了を待ちません。受け付けてから後で結果を取りに来てもらう、非同期の形にします。

  1. 投入クライアントが API にプロンプトを送る。Ingress → api
  2. 受付API はジョブ ID を発行して Redis に積み、すぐ ID を返す。api → data
  3. 取り出しワーカがキューからジョブを取り出す。worker ← data
  4. 推論ワーカが vLLM の Service に問い合わせる。worker → llm
  5. 保存ワーカが結果を Redis に書く。worker → data
  6. 取得クライアントがジョブ ID で結果を取りに来る。Ingress → api → data

エージェント(段階 6〜7)

kagent のセッションは、Substrate 上のアクターとして動きます。段階 7 で agentgateway を入れると、LLM への問い合わせがそこを通ります。

  1. 会話ユーザーが kagent のエージェントに話しかける。クライアント → kagent
  2. セッションセッションが作られ、サンドボックス内のアクターが動く。履歴は PostgreSQL に残る。kagent → substrate
  3. LLM 呼び出しエージェントが LLM に問い合わせる。ModelConfig の向き先が agentgateway になる。substrate → agentgateway
  4. 中継agentgateway が vLLM に中継し、通信をログに残す。agentgateway → llm
  5. ツールツールは kagent の外にある MCP サーバを呼ぶ。RemoteMCPServer で登録する。agentgateway → MCP サーバ

設計判断と理由

決めたこと理由検討した代替
最初から Kind を GCE の VM 1 台で動かすMac は Intel でメモリ 16GB のため、後の段階が動かない。環境を一つにそろえれば、途中で移行する手間がない。VM なら止めている間の課金がディスク代だけになる。Mac で始めて途中で VM へ移る(環境が二つに分かれる)。GKE(常時課金のため不採用)。
VM は小さく始め、必要になったら大きくする段階 1 は軽く、16GB 前後で足りる見込み。メモリを使う段階の前に、停止中にマシンタイプを変えれば、無駄な課金を避けられる。最初から 32GB や 64GB(簡単だが、使わない間も高い)。
kagent は 1.0 を使うOSS への貢献は、現行の main(1.x)が対象になる。0.10.x は 1.0 に置き換えられ、移行手順もない。0.10.x で先に慣れる(軽いが、後でやり直しになる)。
Substrate と PostgreSQL を kagent の前に入れる1.0 の前提で、エージェントはこの上で動く。先に単体で動くことを確かめると、原因を切り分けやすい。kagent と同時に導入(失敗したとき、どこが悪いか分からない)。
worker を 3 台にする案エージェント用のノードを taint で専用にすると、nodeSelector と toleration の練習になる。メモリも分散できる。worker 2 台に同居(軽いが、配置の制御を学べない)。
LLM の通信は agentgateway を通すGateway API に準拠していて、vLLM の登録手順が公式にある。通信のログと上限を一か所で見られる。kagent から vLLM に直接(段階 6 で先に試す)。kgateway は使わない。
API とワーカを Redis で分ける推論が遅くても API が詰まらない。ワーカ数を増やす、Job にするなど、スケールの練習ができる。API から vLLM を直接呼ぶ同期方式(単純だがタイムアウトしやすい)。
namespace を役割で分けるapi、data、worker、llm などの単位が、そのまま RBAC、NetworkPolicy、ResourceQuota の練習単位になる。default に全部(権限や通信の制御を学べない)。
先に手書き、後で GitOps先に kubectl apply で仕組みを理解してから Argo CD に任せると、自動化されていることが分かる。最初から Argo CD(早いが中身が見えにくい)。
Ingress を学んでから Istio に移る段階 1 は素の K8s の動きを見たい。最初から Istio を入れると、Pod の中に proxy が入り、通信が書き換わって、基礎が見えにくくなる。同じ入口を後で置き換えると、違いがはっきり分かる。最初から Istio(重く、基礎が見えにくい)。Istio は扱わない。
予算アラートと VM の再現は Terraform で行う課金が発生せず、失敗しても安全な題材で Terraform を学べる。VM を手で作ってから再現すると、何を設定したかが分かる。壊しても作り直せる、という方針にも合う。コンソールだけで設定する(簡単だが、再現できない)。
バージョンは着手時に確認して固定どの製品も更新が速い。推測せず、公式のリリース情報から決めて CLAUDE.md に記録する。latest タグ(再現できなくなる)。

リスクと、最初に確かめること

kagent 1.0 まわりは新しく、資料も少ないので、動かないことを前提に確認の順番を決めておきます。

リスク確かめ方だめだったとき
Kind の中で gVisor が動かない段階 6a の最初に、WorkerPool でサンドボックスを 1 つ動かす。Kind のノードは Docker コンテナで、権限やカーネルの制約を受ける。別の分離クラス(microvm)を調べる。VM 側の設定が必要になる可能性がある。解決しなければ、原因を記録して 0.10.x に切り替える。
K8s 1.37 以上の Kind ノードイメージが無い段階 0 で、Kind の最新版が対応するノードイメージを調べる。対応版が出るまで、公式が許す範囲で下の版を試す。
メモリが足りない段階ごとに実測し、見積りを直す。VM を 64GB 級に上げる。または使わない段階のものを止める。
資料が少なく、情報が古い公式ドキュメントとリリースノートを最優先にする。0.x 向けの記事は参考程度にする。Issue を調べ、見つからなければ自分で書く。貢献の種になる。
成熟度が alpha かもしれない着手時に、リリースノートと GitHub のリリースページを確認する。壊れる前提で、作り直せる手順(Makefile、README)を残す。
使いたい Ingress controller が終了している段階 1 の F で、Kind の公式ドキュメントと各プロジェクトの現状を確認する。別の Ingress controller を選ぶ。または Gateway API の実装を入口にする。
Ingress をインターネットに公開してしまうファイアウォールを開けないままにして、SSH のポート転送で確認する。公開しない。開けてしまったら、すぐに閉じて設定を見直す。
Istio と agentgateway で、入口の役割が重なるどちらも Gateway API を扱える。段階 4b で Istio の入口を作る前に、GatewayClass で担当を分ける方法を調べる。段階 7 の前に、Istio の入口を片付ける。または、Istio は一部の namespace だけに限る。
Istio のモードの選択で迷うsidecar 方式と ambient 方式がある。着手時に、公式ドキュメントで現在の推奨と、kagent 1.0(Substrate、gVisor)との相性を調べる。通信の仕組みを学ぶ目的に合う方を選ぶ。合わなければ、対象の namespace を絞る。
Terraform の状態ファイルをコミットしてしまう状態ファイルには、請求アカウント ID などが入る。.gitignore に、*.tfstate、.terraform/、*.tfvars を入れてある。コミット前に git status で確認する。気づいたら、履歴から消す方法を調べる。公開前なら、履歴ごと作り直す。

費用を抑える運用

  • 使うときだけ起動する。停止中はディスク代だけが残る
  • 夜間の自動停止(インスタンススケジュール)を設定して、止め忘れを防ぐ
  • 予算アラートを、VM より先に、Terraform で作る。アラートは通知だけで、上限に達しても課金は止まらない
  • 外部 IP は固定せず、Cloud NAT は使わない
  • 最初は通常の VM。慣れたらスポット VM を試す(突然止まることがある)
  • 使わなくなったら VM とディスクを削除する
  • 起動と停止を繰り返すと Kind が壊れることがある。作り直せるよう、クラスタ作成の手順を残しておく
  • 最初は小さな VM で始め、メモリが必要になる段階で、停止中にマシンタイプを変更する。変更できる条件は、公式ドキュメントで確認する

VM の作成と課金に関わる設定は、内容を確認してから実行します。金額は、実際のマシンタイプとリージョンが決まってから料金計算ツールで見積もります。
